# Identity and authentication

Phone + OTP as the primary factor, JWT access tokens, Redis-backed refresh
rotation with reuse detection, and RBAC. All four roles.

## The token model, and why it is split

| | Access token | Refresh token |
|---|---|---|
| Form | JWT (HS256) | 256 random bits, opaque |
| Life | 15 min | 60 days, sliding |
| Stored where | Client memory only | Client secure storage; server keeps **only a SHA-256 hash** |
| Verified how | Signature, no store read | Looked up and rotated in Redis |
| Revocable | No | Yes, immediately |

Access tokens are stateless so the common request path costs no Redis round
trip. That is the whole reason for the split, and it has a price: a revoked
session's access token keeps working until it expires. Fifteen minutes is the
bound on that, and it is why `auth.access_token_ttl` is capped at an hour rather
than a day.

Revocation power lives with the refresh token instead, where it can be exact.

The refresh token is opaque rather than a JWT. There is nothing in it a client
needs to read, and a self-describing 60-day credential invites someone to trust
its claims without asking the server. Its only meaning is "the server recognises
this".

Only the hash is stored, exactly as for a password. Someone who reads the
session store learns which sessions exist but cannot use any of them.

## Silent auto-login

The requirement: **a user who is logged out but holds a valid refresh token is
signed back in without seeing the login screen.**

On app start, and on any `401`:

1. Read the refresh token from secure storage. Absent → login screen.
2. `POST /v1/auth/refresh`.
3. On success, replace the stored token with the new one and continue.
4. On `token_reuse_detected` or `invalid_refresh_token`, wipe storage and show
   the login screen.

The client never decides whether a token is valid or when to refresh. It reacts
to `401` and to the `expires_in` the server states. A client that decides for
itself is a client that disagrees with the server (2.9).

## Rotation and theft detection

Every refresh rotates. A refresh token works exactly once.

Presenting a token that has already been rotated away means a copy exists —
the legitimate client replaced its own. So the whole session is revoked,
including the honest client's current token. Which of the two holders is the
thief cannot be known, and signing the real user out is recoverable where
leaving an attacker signed in is not.

Revocation kills **every** token in the session's family, not just the newest.
After a theft the attacker may hold any token from the family's history.

### The race, and why it is one Lua script

Two refreshes in flight from one device must produce one rotation. As separate
commands there is a window in which both see a valid token: either both mint a
new pair, or the second is treated as theft and signs an innocent user out of
every device.

The swap is therefore a single script: `GETDEL` the old hash, check the session
still exists, record the old hash as spent, install the new one, slide the TTLs.
Whoever removes the key is the one rotation that proceeds.

`TestRotationIsAtomicUnderConcurrency` fires 32 simultaneous rotations at one
token and asserts exactly one succeeds.

Clients should still coalesce concurrent refreshes into one in-flight request:
the server is correct either way, but a client that fires several will see the
losers refused.

### Distinguishing theft from a stale token

A spent hash is kept in `refresh_spent:<hash>` for the session's lifetime, which
is what separates "already rotated — someone has a copy" from "never issued —
a guess". Without it, telling the two apart would mean scanning every family.

Revocation deletes the spent index too. Otherwise a client that signs out and
later presents its discarded token is reported as a theft — and an alarm that
fires on ordinary logouts is one nobody will investigate.

## One-time codes

Six digits is a million possibilities. On its own that is weak; the five-attempt
cap and the lockout window are what make it not, so they are a requirement of
this design rather than a nicety.

- **Generated by rejection sampling.** A random byte mod 10 makes 0–5 likelier
  than 6–9, and a generator with a measurable bias is worth attacking.
- **Stored hashed, salted with the phone number.** Unsalted, six-digit codes
  have only a million possible hashes — one precomputed table would reverse the
  whole store at once.
- **Compared in constant time.** A byte-by-byte comparison leaks how many
  leading digits were right, turning a million-guess search into about sixty.
- **Peeked, not consumed, on a wrong guess**, so a mistyped digit does not
  destroy the code the user is still holding.
- **Consumed atomically on success** (`GETDEL`), so two submissions of one code
  cannot create two sessions.
- **Destroyed on lockout**, so waiting out the window does not leave a live code.

A wrong code and an expired one return the same error. Telling them apart tells
an attacker whether a code is currently live.

The attempt counter's TTL is set on the first failure only. Refreshing it on
every failure would let an attacker hold a number locked out indefinitely by
guessing once a minute — turning a brute-force defence into a denial of service
against the number's owner. The increment and the expiry are one script: as two
commands, a process dying in between leaves a counter with no TTL, which is a
permanent lockout only a manual Redis edit could clear.

## Phone numbers

A phone number here is a credential: the rate-limit key, the OTP key, and the
account identity. `01712345678`, `8801712345678` and `+8801712345678` all
normalise to one identity, so nobody can double their allowance by alternating
format.

Logs and responses carry the masked form. A full number in a log line is
personal data where many people can read it, and an OTP screen showing the whole
number confirms a guess for an attacker.

One account per **(phone, role)**. The same person may be a customer and a
delivery partner, with different permissions; they may not hold two customer
accounts on one number and dodge a per-account limit.

## Roles

Four, fixed: customer, partner, merchant, admin.

Every endpoint names the roles it admits. There is no "any authenticated user"
shorthand and no variant that admits everyone — `Authenticated()` is written as
"every role", so adding a fifth role forces a decision rather than silently
widening access.

**Admin is not a superset.** An admin token reaching a partner endpoint is
almost always a mis-wired route or a confused client, and silently allowing it
hides the bug. Where an admin genuinely acts for another role, the route lists
both.

The 403 does not name the role it wanted: telling an attacker that an endpoint
requires "admin" maps the system for them.

Three endpoints are public, and only three: requesting a code, verifying one,
and refreshing. Sign-in cannot require a token by definition. That fact is
written down in the route table rather than inferred from absent middleware.

## The JWT

Assembled by hand. The format is small and fully specified in one file, and
hand-rolling it removes a dependency from the most security-sensitive path —
along with that library's own history of algorithm-confusion bugs.

The checks that matter:

- **Only HS256.** Honouring the header's `alg` is the classic hole: `none` makes
  every forged token valid, and `RS256` against an HMAC key turns a public key
  into a signing key.
- **Signature before payload.** Nothing in the body is believed until the
  signature verifies. Reading claims first is how verifiers end up acting on
  attacker-supplied data.
- **Issuer checked**, so a staging token cannot be replayed at production.
- **Key at least 32 bytes**, enforced at construction: HS256 is HMAC-SHA256, so
  a shorter key is the weak link.
- **An unknown role is refused, never defaulted.** Defaulting to customer would
  grant access to anyone who could get a typo into a claim.

An expired token gets its own error code, because it is the one case the client
handles silently — one refresh and a retry. Everything else means "sign in
again". That distinction is what makes auto-login invisible.

## Where things live

Sessions, codes and rate counters are in Redis; only the account record is in
Postgres (ADR 0005). TTLs mean expiry is automatic: no sweeper job to write, none
to forget to run, and a revoked session cannot linger because a cleanup task
fell over.

```
session:<id>              hash  user_id, role, device, timestamps
refresh:<hash>            str   session id — the current token only
refresh_spent:<hash>      str   session id — a hash already rotated away
refresh_family:<id>       set   every hash ever issued for this session
user_sessions:<user_id>   set   live session ids, for the device list
otp:<phone>               str   hashed code
otp_attempts:<phone>      str   failure counter
rate:<scope>:<id>         str   fixed-window counter
```

## Failure behaviour

Every store failure is reported, never softened:

- A rate limiter that cannot reach Redis **refuses** the request. One that fails
  open is not a rate limiter.
- A session store that cannot read **errors** rather than reporting "no
  session", which would sign every user out during an outage and report a valid
  token as unknown rather than as something to retry.
- A corrupted rotation reply is an error, not a success. It can only happen if
  the script has been replaced — exactly when a silent misreading is worst.

Two failures are deliberately tolerated, because failing would punish a user for
our outage: clearing the attempt counter after a successful sign-in, and
clearing the pending code on lockout. Both expire on their own.

## SMS

`LogSender` writes the code to the log so a developer can sign in locally. It
**refuses to be constructed in production**: a code in the application log is
readable by everyone with log access, which is far more people than should be
able to sign in as a customer.

A production deployment therefore cannot start until a real gateway is wired in.
That is asserted end to end — the server exits rather than accepting sign-ins it
cannot deliver codes for.

## Testing

- **Unit** — the rules, over in-memory fakes: the attempt cap, rotation, reuse,
  eviction, and every failure branch. The JWT is tested against the ways JWT
  implementations are actually broken, not the happy path.
- **Integration** — real Redis and real Postgres: the atomic swap under 32-way
  concurrency, spent-token detection, family revocation, sliding expiry, and the
  concurrent account creation race.
- **E2E** — the real binary: sign in, auto-login, theft detection, logout,
  brute-force lockout, and the admin-only configuration surface.
